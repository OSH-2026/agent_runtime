# Action Fabric 调研报告

## 摘要

近年来，大语言模型（LLM）驱动的智能体（Agent）系统迅速发展，大语言模型驱动的智能体系统正经历从“语言生成工具”向“复杂任务执行主体”的关键跃迁。然而，尽管模型能力持续提升，现有 Agent 系统在执行层面仍然停留在以 Agent Loop 为核心的隐式控制流范式，其执行路径嵌入于上下文之中，缺乏显式结构表达。这种设计在简单任务中尚可工作，但在复杂任务中导致依赖关系不可见、执行路径不可验证以及恢复机制不可控等一系列系统性问题。现有主流 Agent 系统在执行层面仍存在根本性瓶颈，其核心问题并不在于模型能力，而在于执行语义与系统架构的缺失。

本文提出一种新的系统架构——Action Fabric 与 DAG 调度执行框架，通过引入结构化动作抽象与显式任务图表示，将 Agent 执行从“推理驱动”转变为“调度驱动”。在该架构中，所有工具与系统能力被统一封装为具有完整执行语义的 Action，任务则被表示为有向无环图，并由调度器统一管理执行。该设计不仅显著提升了系统的并发能力与执行效率，还使得执行过程具备可分析、可验证与可恢复的性质。

本文系统性分析了现有 Agent 架构的结构性缺陷，并在调度理论框架下论证了图执行范式的必要性与优越性。我们进一步展示了 Action Fabric 在统一执行语义、支持复杂调度以及构建系统级 Agent 平台方面的潜力。本文认为，该方向代表了 Agent 系统向“模型原生操作系统”演进的关键路径。

## 1. 项目背景

随着大语言模型能力的持续演进，其在推理、规划与工具使用方面的能力显著增强，推动了智能体系统从单轮问答向复杂任务执行的转变。在这一过程中，Agent 系统逐渐承担起跨工具协调、多步骤推理以及环境交互等职责，成为连接模型能力与真实世界任务的重要中介。

早期的语言模型应用主要依赖 prompt engineering，通过精心设计提示词来引导模型生成期望输出。这种方式本质上仍然是静态的推理过程，其能力受限于单轮上下文。随着 ReAct 等方法的提出，模型开始在推理过程中动态调用外部工具，从而具备了执行能力。这一阶段的系统通过“思考—行动—观察”的循环结构，使模型能够在多轮交互中逐步完成复杂任务。然而，这种循环结构本质上仍然以语言模型为中心，其控制流完全依赖模型在上下文中的隐式推理。

随着任务复杂度进一步提升，这种设计逐渐暴露出深层问题。首先，执行路径缺乏显式表示，导致系统无法在执行前进行全局分析，也无法在执行后进行结构化复盘。其次，工具调用之间的依赖关系仅通过上下文间接表达，既不稳定，也难以被系统层理解。再次，由于每一步决策都依赖模型推理，系统执行呈现严格串行特征，从而在延迟与吞吐方面受到严重限制。更为关键的是，一旦执行过程中出现错误，系统缺乏稳定的恢复机制，往往只能通过重新生成上下文或完全重启流程来处理失败。

当前主流 Agent 系统普遍依赖“Agent Loop”执行范式，即模型在每一步根据当前上下文决定下一步行动。这种模式本质上是一种隐式控制流系统：执行路径完全嵌入在上下文中，缺乏显式结构。这一问题在最新研究中被系统性指出：Agent Loop 可以被形式化为一种“单就绪任务调度器”，在任意时刻仅能执行一个动作，其调度决策完全依赖不透明的模型推理 ([arXiv, Apr 2026](https://arxiv.org/abs/2604.11378?utm_source=chatgpt.com))。这种架构导致依赖关系不可见、执行路径不可验证、恢复机制不稳定。

与此同时，工业界广泛采用的 tool calling（工具调用）机制，虽然通过 JSON schema 在一定程度上规范了输入输出，但仍然停留在“函数调用层”，缺乏系统级语义。工具之间的组合关系、执行顺序、并发可能性、失败恢复策略等，均未被建模。

这些问题并非偶然，而是源于当前 Agent 系统的基本设计范式。换言之，问题不在于模型能力不足，而在于执行层缺乏系统化设计。正是在这一背景下，学术界与工业界开始重新审视 Agent 系统的架构基础，并逐步将关注点从“如何让模型更聪明”转向“如何让系统更可控”。

在这一转变过程中，调度理论为理解 Agent 执行提供了重要工具。上述论文通过形式化分析指出，Agent Loop 的行为等价于一种单就绪任务调度器，其核心特征是系统在任意时刻仅能执行一个任务。这一结论不仅解释了现有系统在并发能力上的局限，也揭示了其在执行效率与可控性方面的根本瓶颈。由此可以看出，要实现 Agent 系统的进一步演进，必须在执行层引入显式结构与调度机制，从而突破单任务执行的限制。

AIOS 架构中，提出了一种重要的系统性转向：以 Intent 为输入，以 Structured Action 为执行语义，将“动作”作为系统级一等公民，从而构建完整的任务执行闭环。其中，System Action Fabric 为整个系统的关键中间层，其作用是将零散工具与系统能力统一抽象为结构化动作，并为 Agent Runtime 提供稳定的执行接口。

本项目聚焦 Action Fabric 的设计与实现，旨在构建一个“统一动作抽象，DAG 调度执行”框架，从根本上重构 Agent 的执行层。

## 2. 立项依据

### 2.1 Agent Loop 架构的结构性缺陷

现有 Agent 系统（如 ReAct、AutoGPT、Assistants API）最广泛采用的执行范式是 Agent Loop，即语言模型在每一步根据当前上下文生成下一步行动，并在执行后将结果反馈回上下文。这种模式的直观优势在于实现简单且具有较强的灵活性，但其深层结构却存在一系列难以克服的缺陷。

首先，从执行结构来看，Agent Loop 缺乏全局规划能力。尽管已有工作尝试通过“先规划再执行”的方式改善这一问题，但在实际运行中，系统仍然需要在每一步依赖模型重新推理下一步行动，从而退化为局部决策过程 ([LangChain, Feb 2024](https://www.langchain.com/blog/planning-agents?utm_source=chatgpt.com))。这意味着，系统无法保证执行路径的整体最优性，也无法在执行前对资源分配与调度进行优化。

其次，从性能角度来看，Agent Loop 的串行执行模式带来了显著的效率问题。由于每一次工具调用都需要等待模型推理，系统在执行过程中会产生大量空闲时间。随着任务步骤数量增加，这种延迟会呈线性甚至超线性增长，从而严重影响用户体验与系统吞吐能力。

再次，从系统可靠性角度来看，Agent Loop 缺乏稳定的恢复机制。由于执行路径隐含在上下文中，一旦某一步失败，系统很难准确识别哪些部分可以复用，哪些部分需要重做。这种不确定性往往导致重复执行甚至任务崩溃，降低系统整体稳定性。

最后，从系统工程角度来看，Agent Loop 的执行历史是非结构化文本，难以进行分析、调试与审计。这使得系统在安全性与可解释性方面面临严重挑战，也限制了其在高要求场景中的应用。

### 2.2 Tool Calling 范式的局限

工业界主流解决方案（如 OpenAI Function Calling）通过引入 schema 化接口，提高了工具调用的规范性，但仍存在以下不足：

其一，工具语义仍然松散。不同工具之间缺乏统一语义模型，难以组合与复用。

其二，缺乏执行层抽象。系统只提供“调用能力”，而不提供“执行语义”，例如并发策略、依赖关系、失败恢复等。

其三，缺乏系统级安全机制。权限控制、审计、确认机制通常由上层业务实现，难以统一。

因此，tool calling 本质上仍是“函数级调用”，而非“系统级执行语义”。

### 2.3 Action 抽象的提出

Action Fabric 的核心思想是：将工具调用提升为“结构化动作”，并为其赋予完整的执行语义。

一个 Action 不再只是函数调用，而是一个具有完整描述的执行单元，包括参数 schema、输出定义、权限要求、风险等级、回滚语义以及审计要求。这种设计使得系统可以在不依赖模型推理的情况下，对执行过程进行分析与控制。

更重要的是，Action 之间可以通过参数引用建立显式依赖关系，从而构建任务执行图。这一机制为后续的 DAG 调度提供了基础。

考虑一个需要在 Python 项目中修复 Bug 的任务，该任务包含以下步骤 (如上图)：

- 并行搜索两个模块
- 读取这两个模块的代码内容
- 分析根本原因
- 在两种候选修复方案中选择其一或尝试两种 patch
- 运行测试
- 更新文档
- 生成修复报告

在传统 Agent Loop 范式中，上述流程被完全串行化执行：

- 每一步都依赖上一轮 LLM 推理结果
- 两个模块的搜索无法并行
- 两个文件读取无法并行
- patch 选择与测试执行被强制顺序化
- 总体执行通常需要约 11 个交互轮次（11 turns）
- 一旦某个 patch 失败，恢复方式通常是“重新提示模型”或“重新生成上下文”，缺乏结构化回退机制
- 更关键的是，系统中不存在任何机制能够保证“必须在两个文件都读取完成之后才进行分析”，依赖关系完全隐式存在于上下文中

相比之下，在 DAG 调度框架中，同一任务被显式建模为任务图：

- 两个模块的 search + read 阶段可以并行执行（并发集合大小 |U| = 2）
- 根因分析在两个读取完成后自动触发（依赖显式约束）
- 两种 patch 方案可以并行尝试（并发集合大小 |U| = 3）
- 文档更新与测试执行可在依赖满足后调度执行
- “any-of join” 用于选择最先成功的 patch，并自动跳过失败分支

因此，该任务在 DAG 调度下可压缩为约 6 个调度轮次（6 scheduling rounds）：

- 并发结构由系统调度器决定（|U| = 2 / 3）
- 依赖关系由图结构静态约束
- 容错与恢复由执行语义统一管理，而非 LLM 即时决策

这一对比表明：在 Agent Loop 中，执行效率与正确性高度依赖模型“逐步推理能力”；而在 DAG 执行中，并发性、依赖约束与恢复策略是结构化系统属性，而非模型能力的一部分。

已有研究表明，将 LLM agent 工具调用映射到并行计算框架（如 Parsl）后，可以实现真正的并发执行，从而提升整体任务吞吐量 ([arXiv, Feb 2025](https://arxiv.org/abs/2502.12280?utm_source=chatgpt.com))。

其次，DAG 使执行路径显式化，从而可以进行静态分析与调度优化。这一点与 LangGraph 等框架的设计理念一致，即通过图结构表示任务流，实现状态可视化与可调试性 ([LangGraph](https://docs.langchain.com/oss/python/langgraph/overview))。

再次，DAG 支持增量恢复。节点执行结果可以缓存，失败后仅需重新执行未完成节点，而非重跑整个流程。

### 2.5 总结

基于上述分析，可以看出当前 Agent 系统的核心缺陷在于缺乏统一的执行语义与调度机制。为了解决这一问题，本文提出 Action Fabric 架构，其核心思想是将工具调用提升为具有完整语义的 Action，并通过显式依赖关系构建任务执行图。在此基础上，引入 DAG 调度机制，使系统能够在执行层进行统一管理与优化。

这一设计不仅在理论上回应了调度框架中的关键问题，也在工程上提供了一种可实现的路径。通过将执行控制从模型转移到系统层，Action Fabric 使得 Agent 系统具备了类似操作系统的调度能力，从而为其在复杂任务中的应用奠定基础。

## 3. 前瞻性与重要性分析

### 3.1 从 Agent Loop 到 Graph Execution 的演进趋势

从技术发展趋势来看，Agent 系统正在经历一次从“循环执行范式”向“结构化图执行范式”的深刻转变。这一转变不仅是工程层面的优化，更是系统范式的根本变化。在传统 Agent Loop 中，控制流嵌入在语言模型的上下文之中，其执行路径由模型在运行时动态决定；而在图执行范式中，控制流被显式表示为任务图，执行调度由系统统一管理。这种转变意味着，Agent 系统的核心能力正在从“推理能力”转向“执行能力”。

最新研究明确指出，LLM Agent 正在从“循环执行范式”向“结构化图执行范式”演进 ([arXiv, Apr 2026](https://arxiv.org/abs/2604.11378?utm_source=chatgpt.com))。这一转变不仅是工程优化，更是系统范式的改变。

在这一新范式中：

- 控制流从隐式上下文转移为显式图结构  
- 执行调度从模型决策转移为系统调度  
- 错误恢复从启发式回溯转移为结构化策略  

本项目提出的 Action 与 DAG 机制，正是这一趋势的工程化实现。

### 3.2 并发与调度成为核心瓶颈

随着 Agent 系统复杂度提升，执行效率问题日益突出。最新系统研究（如 Continuum）指出，多轮 agent workflow 中，tool call 带来的“执行间隙”会严重影响系统吞吐与延迟 ([arXiv, Nov 2025](https://arxiv.org/abs/2511.02230?utm_source=chatgpt.com))。因此，调度机制成为系统性能的关键因素。

在这一背景下，并发与调度逐渐成为系统性能的关键瓶颈。随着任务规模的扩大，单一模型调用的延迟已不再是主要问题，真正影响系统效率的是多轮工具调用之间的等待时间。在复杂任务中，大量时间消耗在模型推理与工具执行之间的空隙，这种“执行间隙”成为限制系统吞吐的主要因素。通过引入 DAG 调度与并发执行，可以显著减少这一间隙，从而提升整体性能。

本项目通过 DAG 调度与并发执行，从根本上优化这一问题，使工具调用从“串行瓶颈”转变为“可调度资源”。

### 3.3 向操作系统级 Agent 演进

从更宏观的角度来看，Action Fabric 的意义不仅在于优化 Agent 执行效率，更在于推动 Agent 系统向操作系统级架构演进。在 AIOS 架构中，Action Fabric 被视为系统能力总线，使得所有能力都通过统一协议暴露，从而实现跨应用、跨设备的任务执行。

在 AIOS 的愿景中，所有系统能力都通过统一的 Action 接口暴露，调度器负责管理资源与执行策略，而语言模型则作为高层规划器参与决策。这种架构与传统操作系统具有高度相似性，其核心在于将复杂执行逻辑从应用层下沉到系统层，从而实现统一管理与优化。

这意味着，本项目不仅是一个 Agent 框架，更是未来“模型原生操作系统”的基础组件。可以预见，随着 Agent 系统在各类应用中的普及，其执行复杂度将持续提升。在这一过程中，缺乏结构化执行语义与调度机制的系统将难以扩展，而基于 Action Fabric 与 DAG 调度的架构则具备更强的适应性与扩展性。因此，该方向不仅具有重要的理论价值，也具有显著的工程意义。

## 4. 相关工作

在过去两年中，围绕大语言模型的 Agent 系统已经形成了多个研究方向，包括基于循环推理的 Agent Loop 方法、结构化规划方法、图结构执行框架以及并发调度系统等。这些工作从不同角度探索了如何提升 Agent 的执行能力，但在执行语义与系统架构层面仍存在明显不足。

### 4.1 图结构 Agent 框架

近年来，LangGraph 成为最具代表性的图结构 Agent 框架。其核心思想是将 Agent workflow 表示为有向图，节点为函数或 Agent，边表示状态流转。开发者可以定义完整的状态机，并对每个节点进行精细控制 ([LangGraph](https://docs.langchain.com/oss/python/langgraph/overview))。这类系统通过将任务表示为有向图，使得开发者可以显式定义状态流与执行路径，从而实现并发执行与状态管理。相比 Agent Loop，这种方法在执行效率与可控性方面具有明显优势。然而，其节点语义通常仍然是函数调用，缺乏统一的执行语义模型，同时在权限控制、审计机制以及恢复策略方面仍依赖上层实现，未形成完整系统抽象。

LangGraph 的一个重要特性是支持并发执行与依赖解析。通过 DAG 结构，系统可以自动识别可并行执行的子任务，从而提升执行效率 ([Emergent Mind](https://www.emergentmind.com/topics/langgraph?utm_source=chatgpt.com))。此外，其持久化状态机制允许系统在崩溃后恢复执行，这一点与本项目的“缓存输出，增量恢复”设计高度一致。

然而，LangGraph 仍存在明显局限。首先，它是开发框架而非系统层抽象，缺乏统一的权限与审计机制。其次，其节点语义仍然是“函数”，而非“动作”，缺乏统一的执行语义模型。

### 4.2 结构化规划方法

最早一类工作以 ReAct 为代表，其核心思想是在推理过程中交替生成“思考”和“行动”，通过多轮交互逐步完成任务。这类方法的优势在于灵活性强，能够适应开放环境中的不确定性。然而，其执行过程完全依赖模型推理，缺乏显式结构表示，从而在复杂任务中表现不稳定。AutoGPT 等系统在此基础上进行了扩展，引入长期记忆与自动化执行机制，但其核心执行模式仍然是 Agent Loop，因此并未从根本上解决结构性问题。

Plan-and-Execute 方法是对 ReAct 的重要改进。该方法要求模型先生成完整计划，再执行各个子任务，从而减少模型调用次数并提升执行质量 ([LangChain, Feb 2024](https://www.langchain.com/blog/planning-agents?utm_source=chatgpt.com))。这类方法在一定程度上减少了模型调用次数，并提升了执行稳定性。然而，在实际运行中，由于环境的不确定性与计划的不完备性，系统往往需要在执行过程中动态调整计划，从而重新回到逐步推理的模式。因此，该方法本质上仍然依赖 Agent Loop，其改进主要体现在规划层，而非执行层。

进一步的工作如 Routine 框架，通过引入结构化计划模板与参数传递机制，大幅提升工具调用准确率，最高可提升至 96% 以上 ([arXiv, Jul 2025](https://arxiv.org/abs/2507.14447?utm_source=chatgpt.com))。这表明，结构化规划本身是提升 Agent 稳定性的关键因素。

然而，这类方法仍停留在“规划层”，缺乏与执行层的深度结合，特别是缺乏统一调度机制。

### 4.3 并发执行与任务图调度

在系统领域，已有大量关于 DAG 调度的成熟工作，如 Airflow、Ray、Dask 等。这些系统提供了任务依赖管理、并发执行与失败恢复机制。

在 Agent 领域，最新研究开始将这些思想引入。例如 DynTaskMAS 框架提出“动态任务图生成，异步并发执行”，在复杂任务中实现 21–33% 的执行时间优化 ([ArXCompass](https://arxcompass.github.io/papers/llm/2025_12/papers_10.html?utm_source=chatgpt.com))。

此外，将 Agent 工具调用接入 HPC 调度系统（如 Parsl）后，可以实现真正的并行执行，验证了 DAG 调度在 Agent 场景中的可行性 ([arXiv, Feb 2025](https://arxiv.org/abs/2502.12280?utm_source=chatgpt.com))。

### 4.4 Agent 调度与系统优化

最新系统研究（如 Continuum）开始从系统层优化 Agent 执行，通过预测 tool call 时间并优化 KV cache 生命周期，从而减少延迟并提升吞吐 ([arXiv, Nov 2025](https://arxiv.org/abs/2511.02230?utm_source=chatgpt.com))。这说明，Agent 系统正在逐步从“模型问题”转向“系统问题”。

## 5. 详细设计

### 5.1 DAG 调度的核心形式化定义

#### 5.1.1 执行计划

一个执行计划是一个元组：
$$
\Pi = (id, version, V, E, \sigma, \kappa)
$$
其中：

- id：计划唯一标识符
- version：计划版本号，用于支持演化与回溯
- V：节点集合（set of nodes），表示所有执行任务
- $E \subseteq V \times V$：有向边集合，表示节点间依赖关系
- $\sigma : V \rightarrow NodeConfig$：节点配置函数，为每个节点分配执行配置，包括：
  - action 类型
  - 重试策略（retry policy）
  - 副作用级别（side-effect level）
  - 资源需求等
- $\kappa$：输出契约（output contract），定义执行完成后必须产出的结果结构

该定义强调三个关键点：

1. 执行结构显式化：任务不再隐含在 prompt 中，而是结构化为图
2. 执行语义可计算：每个节点具有明确 configuration，可被调度器解析
3. 输出可验证性：$\kappa$ 将“任务完成标准”从自然语言提升为结构约束

#### 5.1.2 Join 模式

##### 5.1.2.1 All-of Join

对于节点 v，其前驱集合为 P，当且仅当满足以下条件时，该节点进入 ready 状态：
$$
ready_{all\_of}(v) \iff \forall p \in P : \sigma(p) = executed
$$
含义：

- 只有当所有前驱节点均成功执行完成（executed）
- 当前节点才被调度器加入可执行队列（ready set）

适用场景：

- 多信息源融合（例如多文件分析后统一总结）
- 严格依赖型计算流程
- 数据一致性要求较高的任务

##### 5.1.2.2 Any-of Join

对于候选集合 C，其语义如下：

（1）分发规则（Dispatch）

- 所有依赖满足的候选节点 $c \in C$ 将被调度执行
- 执行顺序为确定性全序（deterministic total order），例如按 node id 升序
- 该顺序完全由 DAG 结构决定，与运行时状态无关

（2）成功传播（Success Propagation）

一旦存在某个候选节点 $c^* \in C$ 达到执行成功状态：
$$
ready_{any\_of}(v) \iff \exists c \in C : \sigma(c) = executed
$$
则：

- 节点 v 进入 ready 状态
- 表示该 join 已获得有效结果

（3）兄弟节点跳过（Sibling Skip）

当 $c^*$ 成功后：

- 所有尚未进入终态的兄弟节点 $C \setminus \{c^*\}$ 将被标记为 skipped
- 状态包括：pending / ready / running / retryable failed
- 已处于终态（executed / failed / cancelled）的节点保持不变

（4）失败传播（Failure Propagation）

如果所有候选节点均进入终态失败：

- 即所有 $c \in C$ 满足 failed 或 cancelled
- 则该 join 节点 v 进入 failed 状态

### 5.2 分层架构设计

#### 5.2.1 Execution Layer（执行层）

执行层负责执行 Planner (LLM) 生成的计划 $\Pi$，其核心特性包括：

- 输入为静态 DAG(V, E)
- 不允许修改图结构
- 维护每个节点状态（pending / ready / running / executed / failed / skipped）
- 动态计算 ready set
- 执行 Action 并记录 observation
- 向 Recovery Layer 上报失败信息

值得注意的是，执行层不做决策，只做调度与执行。即：

- 不决定如何修复
- 不修改 DAG
- 不重新规划结构

其本质是一个确定性调度执行引擎（deterministic execution engine）。

#### 5.2.2 Recovery Layer（恢复层）

恢复层是独立于执行循环的诊断与修复系统，其职责包括：

- 接收执行层上报的失败信息
- 诊断失败根因（root cause analysis）
- 从 Planner 申请并取回恢复策略（recovery action）

关键特点：

- 与执行上下文隔离
- 不直接参与 DAG 调度
- 基于“诊断上下文（diagnostic context）”决策
- 可触发：
  - 局部重试
  - 子图重规划
  - Patch DAG 插入

## 6. 创新点

本项目的核心创新在于，将“Action 抽象”与“DAG 调度”深度结合，构建一个完整的执行语义层。

首先，在抽象层面，本项目将所有工具统一封装为 Action。每个 Action 具有严格定义的输入输出 schema，并支持参数引用，从而实现动作之间的显式依赖。这一设计使得任务可以被建模为一个可分析的结构。

其次，在执行层面，引入 DAG 调度器。Planner 输出的 Action 序列将被解析为图结构，调度器根据依赖关系自动执行节点，并支持并发执行。相比传统 Agent Loop，这种方式显著提升执行效率，并降低模型调用次数。

再次，在错误恢复方面，本项目引入输出缓存与 patch 机制。当某个节点失败时，系统不会回滚整个流程，而是保留已完成节点的结果，并允许 Planner 生成补丁计划。这一机制显著提升系统鲁棒性。

最后，在系统实现上，本项目选择 Rust + Android NDK 的技术路线，以实现高性能与系统级集成能力。通过 Rust 的安全性与并发能力，可以高效实现调度器与执行引擎。

## 7. 总结

综上所述，当前 Agent 系统的发展已经进入一个关键阶段，其核心挑战不再是模型能力的提升，而是执行系统的重构。通过引入结构化 Action 与 DAG 调度机制，本文提出了一种新的执行范式，从根本上解决了现有系统在并发、可控性与恢复能力方面的结构性问题。

Action Fabric 阶段的研究处于当前 Agent 技术演进的关键节点。通过引入结构化 Action 与 DAG 调度机制，本项目不仅解决了现有 Agent 系统在执行层的核心问题，也为未来“模型原生操作系统”的实现提供了基础。

与现有工作相比，本项目的独特价值在于：不仅关注“如何调用工具”，而是重新定义“什么是执行”；不仅提供“规划能力”，而是构建“执行语义”；不仅优化单个 Agent，而是为整个系统提供统一的能力总线。

本文的核心观点可以概括为：Agent 的未来不在于更强的推理能力，而在于更强的执行系统；而执行系统的核心，不在于调用能力，而在于调度能力。这一方向已经在最新研究中得到验证，并正在成为 Agent 系统发展的主流趋势。完成 Action Fabric 的实现，将为后续 Agent Runtime、Policy、安全体系等模块奠定坚实基础。
