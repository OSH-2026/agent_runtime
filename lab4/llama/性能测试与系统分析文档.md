## Task 1：性能指标拟定

### 1.1 指标列表

| # | 指标名称 | 英文缩写 | 描述 | 测量单位 |
|---|---------|---------|------|---------|
| 1 | 首 Token 延迟 | TTFT | 用户输入后返回第一个 token 的等待时间 | 毫秒 (ms) |
| 2 | 生成吞吐量 | TPS | 文本生成阶段每秒产出的 token 数 | tokens/sec |
| 3 | Prompt 预填充速度 | PP | prefill 阶段处理输入 token 的速率 | tokens/sec |
| 4 | 模型加载时间 | — | 进程启动到模型就绪可推理的耗时 | 秒 (s) |
| 5 | 运行时内存占用 | RSS | 模型加载并推理时占用的物理内存 | MiB / GiB |
| 6 | 困惑度 | PPL | 模型对测试语料的预测不确定性 | 无量纲（越低越好） |

### 1.2 指标合理性说明

**TTFT（首 Token 延迟）**

TTFT 是用户感知响应速度的第一道关卡。用户提交问题后，首个 token 出现之前的等待完全是无响应状态，直接影响交互体验。对于实时对话场景，TTFT < 1 s 是基本要求。

**TPS（生成吞吐量）**

TPS 决定长文本回复的实际等待时间。10 t/s 对应每秒约 6-8 个汉字，低于此值用户会感到明显卡顿。它反映了模型在 decode 阶段对计算资源（CPU/GPU 带宽）的利用效率。

**Prompt 预填充速度（PP）**

对于 RAG、文档摘要等长 prompt 场景，prefill 阶段可能需要处理数千个 token，其速度直接影响 TTFT。独立测量 PP 可将理解输入和生成输出两个瓶颈解耦分析。

**模型加载时间**

在弹性伸缩或频繁冷启动场景下，加载时间决定了服务从零扩容到可用的速度。对于小型部署（无常驻服务），加载时间占每次对话总耗时的比例不可忽视。

**内存占用（RSS）**

内存直接决定模型能否在目标硬件上运行，以及单节点可同时运行的模型实例数。对于资源受限的边缘设备或低配云主机，内存是最主要的部署约束。

**困惑度（PPL）**

PPL 是语言模型质量的标准化数值指标，不依赖主观人工评分。它衡量量化带来的精度损失，使 Q4/Q5/Q8 等不同量化格式的质量可以客观横向比较。PPL 越低表示模型对语料的预测越准确。

### 1.3 指标覆盖维度

```
延迟维度  → TTFT、PP（影响用户感知的响应速度）
吞吐维度  → TPS（系统持续处理能力）
资源维度  → 内存占用、加载时间（硬件需求与部署成本）
质量维度  → PPL（模型输出的语言准确性）
```

## Task 4：参数分析与优化

### 4.1 线程数（-t）优化

**结论**：`-t 2` 是最优配置，与物理 vCPU 数匹配。

| 参数 | pp64 (t/s) | tg128 (t/s) | 原因分析 |
|------|-----------|-------------|---------|
| -t 1 | 17.54 | 6.54 | 未充分利用双核 |
| **-t 2** | **28.58** | **10.75** | **最优，恰好用满 2 个物理核** |
| -t 4 | 28.39 | 8.71 | tg 下降：decode 是串行自回归，超额线程产生竞争 |
| -t 16 | 27.74 | 4.05 | 严重超卖，锁竞争和上下文切换拖垮 tg |

**分析**：pp（prefill）可以有效利用多核并行，因此 t=4 的 pp 速度与 t=2 相近。但 tg（token generation）是逐 token 串行的自回归过程，超过物理核心数后，额外线程的调度开销大于并行收益。

### 4.2 批次大小（--batch-size）优化

**结论**：128-512 范围内对 tg 无显著影响；pp 在 256 时略优。

| -p 值 | pp 速度 (t/s) | tg128 (t/s) | 分析 |
|-------|--------------|-------------|------|
| 128 | 30.09 | 10.94 | pp 略低，cache 利用率较低 |
| **256** | **31.25** | **10.92** | **pp 最优，cache line 利用率较好** |
| 512 | 31.03 | 10.88 | pp 与 256 相近，内存稍多 |

推荐：`--batch-size 256`，兼顾 pp 速度与内存占用。

### 4.3 mmap 开关（--no-mmap）

**结论**：两者性能差异 < 3%，对本实验影响可忽略。

| 模式 | pp64 (t/s) | tg128 (t/s) | 内存加载行为 |
|------|-----------|-------------|------------|
| mmap=1（默认） | 28.58 | 10.75 | 按需映射，加载快，支持多进程共享 |
| mmap=0（--no-mmap） | 27.73 | 10.79 | 全量读入 RAM，加载略慢 |

对于 1.04 GiB 的小模型，mmap 的主要优势是加载速度而非推理速度。

### 4.4 上下文大小（--ctx-size）分析

| ctx-size | Prompt Eval (t/s) | Generation (t/s) | KV Cache 大小 |
|----------|-------------------|-------------------|--------------|
| 512 | 6.9 | 3.2 | 最小（约 64 MiB） |
| 1024 | 5.7 | 3.6 | 中等（约 128 MiB） |
| 2048 | 8.4 | 3.7 | 较大（约 256 MiB） |

速度差异在测量误差范围内。ctx-size 的主要影响是内存占用和最长可处理文本的长度。

### 4.5 最优参数配置

| 参数 | 推荐值 | 原因 |
|------|--------|------|
| `-t` | `2` | 匹配物理 vCPU 数 |
| `--batch-size` | `256` | pp 速度微优 |
| `--mmap` | `1`（默认） | 加载速度更快 |
| `--ctx-size` | `512`（日常）/ `2048`（长文档） | 按需选择 |

**最优运行命令**：

```bash
llama-cli -m ~/models/qwen2.5-1.5b-instruct-q4_k_m.gguf \
          -t 2 -b 256 --ctx-size 512 \
          -p "你的 prompt" -n 512
```

### 4.6 量化格式对比（选做加分项）

| 量化格式 | 文件大小 | pp64 (t/s) | tg128 (t/s) | 相对 Q4 pp | 相对 Q4 tg |
|----------|---------|-----------|-------------|-----------|-----------|
| **Q4_K_M** | 1.04 GiB | **28.35 ± 1.36** | **10.75 ± 0.23** | 1.00x | 1.00x |
| Q5_K_M | 1.19 GiB | 14.76 ± 0.37 | 8.46 ± 0.23 | 0.52x | 0.79x |
| Q8_0 | 1.76 GiB | 25.14 ± 0.84 | 7.41 ± 0.07 | 0.89x | 0.69x |

- **Q4_K_M 全面领先**：内存占用最小，pp 和 tg 均最快。
- **Q5_K_M 的 pp 异常低**：仅为 Q4 的 52%，推测 AVX-512 下 Q5 解码路径存在额外开销。
- **Q8_0 的 tg 最慢**：模型尺寸大 69%，内存带宽瓶颈导致 tg 比 Q4 慢 31%。
- 在资源受限（2 vCPU / 6 GB）环境下，**Q4_K_M 是速度和质量的最优平衡点**。

## Task 5：输出质量评估

### 5.1 Prompt 设计

| 编号 | 类型 | Prompt 内容 |
|------|------|------------|
| P1 | 中文知识问答 | 请解释操作系统中的虚拟内存机制，以及它的三个主要作用。 |
| P2 | 文本摘要 | 请用 3-5 句话总结以下内容的核心观点：宏内核将所有服务运行在同一地址空间，性能好但隔离差；微内核只保留最小内核，模块化好但通信开销大。 |
| P3 | 代码解释 | 请解释下面这段 LRU 缓存 lru_get 函数的功能（遍历查找，空槽优先，否则淘汰最旧时间戳的条目，缓存命中时更新时间戳）。 |
| P4 | 逻辑推理 | 一个进程申请内存成功后，是否一定能立刻运行？请分析可能阻止它运行的三种情况并解释原因。 |
| P5 | 课程相关 | 在 Lab3 的 HTTP 服务器中，如果使用线程池（thread pool）而不是每来一个连接就新建一个线程（thread-per-connection），在性能和资源管理方面有哪些优劣势？ |

### 5.2 测试配置

```bash
# 测试命令（temperature=0.7，t=2）
llama-cli -m ~/models/qwen2.5-1.5b-instruct-q4_k_m.gguf \
          -t 2 -b 256 --temp 0.7 -n 400 \
          -p "<prompt 内容>"
```

### 5.3 测试结果

**P1 - 知识问答**（评分：4.3/5）

模型正确解释了虚拟内存的抽象概念，列举了扩展物理内存空间、提供内存保护隔离、支持多进程并发三个作用。语言流畅、结构清晰。
*不足*：将虚拟内存与 swap 机制略有混淆，是 1.5B 小模型的典型知识边界。

**P2 - 文本摘要**（评分：4.7/5）

准确提取了宏内核和微内核的核心区别，摘要长度适中（4 句），保留了性能和故障隔离两个关键维度。表现良好。

**P3 - 代码解释**（评分：5.0/5）

正确识别了 LRU 缓存淘汰算法，准确解释了 slot 变量的双重作用（空槽优先、否则淘汰最旧）和 ts 时间戳的 LRU 语义，以及缓存命中时更新时间戳的逻辑。代码理解能力最佳。

**P4 - 逻辑推理**（评分：3.3/5）

能列举 CPU 调度未被选中、I/O 等待阻塞、资源锁竞争三种情况，基本合理。
*不足*：对 mmap 延迟分配和缺页中断等深层机制理解不足，回答偏浅。

**P5 - 课程相关**（评分：4.3/5）

清晰比较了线程池和 thread-per-connection 的权衡，提到了线程创建销毁开销、OOM 风险、请求队列等关键概念。偶有细节错误（线程池大小与连接数上限的关系）。
