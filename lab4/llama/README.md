## Task 1: 性能指标拟定（8分）

### 1.1 指标列表与合理性说明

| 指标 | 描述 | 合理性说明 |
|------|------|-----------|
| **TTFT** (Time to First Token) | 用户输入后生成首个 token 的时间 | 直接影响用户体验，是衡量推理延迟的核心指标。低 TTFT 意味着用户能更快看到响应开始 |
| **TPS** (tokens/sec, 生成吞吐) | 文本生成阶段的 token 产出速率 | 反映模型的持续输出能力，决定长文本回复的等待时间。TPS 越高，用户体验越流畅 |
| **Prompt Eval 速度** (t/s) | 预填充阶段处理 prompt token 的速度 | 影响模型"理解"输入的时间，对长 prompt 场景（RAG、文档分析）尤为关键 |
| **模型加载时间** | 从启动到模型就绪可用的耗时 | 影响服务部署速度和冷启动延迟，对弹性伸缩和频繁更新模型的场景重要 |
| **内存占用** (RSS) | 模型运行时占用的物理内存 | 决定部署成本——能否在资源受限设备上运行，以及单机可同时部署的模型数量 |
| **Perplexity (困惑度)** | 模型对测试语料的预测困惑度 | 衡量模型对语言的理解能力，PPL 越低表示模型对文本的预测越准确，是量化后质量对比的标准指标 |

### 1.2 指标选择依据

以上 6 个指标覆盖了 LLM 推理的四个维度：
- **延迟维度**（TTFT、Prompt Eval）：用户感知的响应速度
- **吞吐维度**（TPS）：系统的持续处理能力
- **资源维度**（加载时间、内存占用）：部署的硬件需求和成本
- **质量维度**（Perplexity）：模型输出的语言质量

## Task 4: 参数分析与优化（15分）

### 4.1 线程数 (`-t`) 对性能的影响

| 线程数 | pp64 (t/s) | tg128 (t/s) | 分析 |
|--------|-----------|-------------|------|
| 1 | 17.54 | 6.54 | 单核瓶颈 |
| **2** | **28.58** | **10.75** | **最优** |
| 4 | 28.39 | 8.71 | tg 开始下降 |
| 16 | 27.74 (pp512) | 4.05 | 严重争抢 |

**结论**：2 线程最优，恰好匹配 2 vCPU 物理核心数。超过物理核心数后线程竞争导致性能下降，尤其是 tg（逐 token 生成）对线程切换更为敏感。

### 4.2 批次大小 (`-p`) 对性能的影响

| prompt 长度 | pp 速度 (t/s) | tg 速度 (t/s) |
|-------------|--------------|---------------|
| 128 | 30.09 | 10.94 |
| 256 | 31.25 | 10.92 |
| 512 | 31.03 | 10.88 |

**结论**：批次大小在 128-512 范围内对 pp 和 tg 影响不大。pp 速度在 256 时略优（更好的 CPU cache 利用率），但差异不足 5%。tg 速度几乎完全不受影响——这符合预期，因为 tg 是逐 token 生成的，不依赖批次大小。

### 4.3 mmap 对性能的影响

| 模式 | pp64 (t/s) | tg128 (t/s) |
|------|-----------|-------------|
| mmap=1 (默认) | 28.58 | 10.75 |
| mmap=0 | 27.73 | 10.79 |

**结论**：mmap 对性能影响极小（< 3%）。对于 1.04 GiB 的小模型，内存直接加载 vs 文件映射的性能差异可忽略。mmap 的优势主要在于模型加载速度和多进程共享内存。

### 4.4 上下文大小（--ctx-size）对性能的影响

使用 `llama-cli` 测试不同上下文窗口大小时的实际推理速度（固定 prompt，t=2）：

| ctx-size | Prompt Eval (t/s) | Generation (t/s) | 说明 |
|----------|-------------------|-------------------|------|
| 512 | 6.9 | 3.2 | 默认值，KV cache 最小 |
| 1024 | 5.7 | 3.6 | 支持更长上下文 |
| 2048 | 8.4 | 3.7 | 支持更长上下文 |

> 注：此处 llama-cli 的绝对速度低于 llama-bench，因使用完整 chat template 格式和较短的测试 prompt，测量变异性较大。

**分析**：
- ctx-size 对短 prompt（< 100 tokens）的推理速度影响不大，差异在测量误差范围内
- 主要影响在**内存占用**：ctx-size 从 512 增加到 2048 时，KV cache 大小按比例增长
- 对于本实验的 2 vCPU / 6GB RAM 环境，512-2048 的 ctx-size 均能正常运行
- 推荐：日常问答使用 512（节省内存），长文档处理使用 1024-2048

### 4.5 最优配置

```
推荐参数：-t 2 -b 512 --mmap 1
```

- 线程数 = 物理核心数（2）
- 批次大小取中间值（512），兼顾吞吐与内存
- 保持默认 mmap，加快加载速度

## Task 7: 单机 vs RPC 对比（10分）

### 7.1 性能对比

| 运行方式                      | Prompt 处理速度 (t/s) | 生成吞吐量 (t/s) |
| ----------------------------- | --------------------- | ---------------- |
| 从机1（单机本地推理）         | 306.2                 | 73.2             |
| 从机2（单机本地推理）         | 315.1                 | 69.6             |
| 主机调用（仅从机1 RPC）       | 226.3                 | 68.2             |
| 主机调用（从机1 + 从机2 RPC） | 209.7                 | 52.7             |

> 注：单机本地推理数据使用 `tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf` 测得，与主机 RPC 调用使用相同模型以保证可比性。

### 7.2 原因分析

1. **RPC 通信开销**：每次请求需要将 token、激活值、中间状态等数据打包并通过网络传输。Prompt 处理阶段数据量大（需传输整个 prompt 的嵌入），导致速度明显下降。
2. **网络延迟**：即使是本地回环（127.0.0.1）或低延迟局域网，每次 RPC 调用的往返延迟（RTT）也会累加。Prompt 处理需要多次跨节点交互，对延迟敏感。
3. **双从机模型切分与同步**：llama.cpp 的 RPC 后端默认按层（layer）切分模型。两个 Worker 各承担部分层，Master 需要等待两者都完成才能继续。若切分不均或 Worker 速度不一（本实验中从机2 的 tg 速度稍慢），则快 Worker 必须等待慢 Worker，形成同步瓶颈。
4. **负载不均衡**：双从机并行时，整体性能受限于较慢的环节。本实验中双机 RPC 的生成吞吐（52.7 t/s）甚至低于单从机 RPC（68.2 t/s），说明通信与同步开销超过了并行带来的收益。
5. **模型太小**：TinyLLaMA-1.1B 本身计算量小，单机已能接近内存带宽上限。分布到多机后，通信开销占比显著增大，导致得不偿失。对于大模型（如 7B+），RPC 分布式推理才可能体现优势。

### 7.3 结论

- 在 **小模型 + 高速单机** 场景下，RPC 分布式推理的性能不如单机直接推理。
- 网络延迟和同步开销是主要性能杀手。
- 分布式推理适合 **单机放不下的大模型**（如 70B 需多机显存聚合），或 **计算量远大于通信量** 的场景。

## 选做一：量化格式对比 (Q4_K_M vs Q5_K_M vs Q8_0)

### 模型信息

| 量化格式 | 文件大小 | 位深 | 方案 |
|----------|---------|------|------|
| Q4_K_M | 1.04 GiB | ~4.5 bit | K-quant 混合精度 |
| Q5_K_M | 1.19 GiB | ~5.5 bit | K-quant 混合精度 |
| Q8_0 | 1.76 GiB | 8 bit | 均匀量化 |

### 性能对比 (llama-bench, t=2, pp64, tg128)

| 量化格式 | pp64 (t/s) | tg128 (t/s) | 相对 Q4 的 pp | 相对 Q4 的 tg |
|----------|-----------|-------------|--------------|--------------|
| **Q4_K_M** | **28.35 ± 1.36** | **10.75 ± 0.23** | 1.00x (基准) | 1.00x (基准) |
| Q5_K_M | 14.76 ± 0.37 | 8.46 ± 0.23 | 0.52x | 0.79x |
| Q8_0 | 25.14 ± 0.84 | 7.41 ± 0.07 | 0.89x | 0.69x |

### 分析

1. **Q4_K_M 是速度最优选择**：在所有指标上均领先。pp64 速度几乎是 Q5_K_M 的 2 倍，tg128 也高出 27%。对于 1.5B 小模型，4-bit 量化在性能和质量之间取得了最佳平衡。

2. **Q5_K_M 的意外低性能**：pp64 仅为 Q4 的 52%。这与 K-quant 的实现细节有关：Q5_K_M 在 AVX-512 指令集下的解码路径可能不如 Q4_K_M 优化充分，导致 prompt 处理时更多计算开销。

3. **Q8_0 的高 pp 速度**：作为简单的均匀 8-bit 量化，Q8_0 享有更简单的解码逻辑。但其 tg 速度（7.41 t/s）不如 Q4_K_M，因为更大的模型尺寸导致更高的内存带宽需求。

4. **内存与速度的 Tradeoff**：模型越大，内存带宽瓶颈越明显。Q8_0 相比 Q4_K_M 大了 69%，但 tg 速度下降了 31%。

### 质量预期

虽然本实验未对输出质量做系统对比（需要更长文本和多维度人工评估），根据 Qwen 官方和社区基准：
- Q4_K_M：日常任务可接受，偶有轻微退化
- Q5_K_M：接近 FP16 质量，推荐的质量-大小平衡点
- Q8_0：几乎无损，适合对质量要求高的场景

### 推荐

对于 resource-constrained 的单机部署（如本实验的 2 vCPU / 6 GB RAM 环境），**Q4_K_M 是最佳选择**：加载快、推理速度快、质量可接受。如果磁盘空间允许且对质量有更高要求，Q5_K_M 是更好的质量选择但需接受约 50% 的速度惩罚。
